# The other flows we need
A one-screen product still needs complete states. Put secondary flows in sheets, menus and contextual cards, not permanent primary navigation.

## Repeat value, not engagement for its own sake
After a user has repeated a supported sequence, suggest saving it as a recipe: "Do this often? Save the steps." An entitled saved recipe contains operation IDs/settings, not a server-uploaded copy of the source files. On replay choose new local files, confirm relevant parameters and execute without unnecessary AI calls. Keep filenames, personal recipe titles and source paths local.

Returning users can select recent local jobs or recipes from a small secondary menu. Clearly distinguish a stored output from a missing file handle. Do not show a downloadable result that no longer exists. Give a precise reimport action and preserve non-sensitive recipe settings. Browser storage is not durable cloud backup; disclose eviction/private-browsing limits. No automatic sync promise.

## Permission and communication policy
No notification, contacts, location, broad storage or camera prompt at first launch. Use system file/photo pickers for the selected scope. Camera capture is not required for this launch. Downloading OCR language assets can have a progress state and a metered-network notice; that is not an LLM download.

Offer a completion notification only for a genuinely long-running job if the platform can reliably finish it in the background. Do not promise background processing on an OS that may suspend it. A permission denial is not an error and never blocks the job. User-requested routine reminders should be optional, specific and disabled by default. No daily guilt messages for not using PDF software.

Separate transactional purchase/security/service messages from opted-in educational marketing. A welcome email needs a real verified address and suitable consent; it cannot be sent to an anonymous user. Clear unsubscribe, frequency cap and data deletion rules are required. No guessed customer-email collection from documents.

## Reviews and referrals
A system review request can be considered after two successful user-file sessions, away from an active job, purchase or permission prompt. This is a starting scheduling hypothesis, not a claim the OS will show it. Do not ask "Do you love us?" then route only happy users to public reviews; use platform mechanisms and never incentivize ratings.

An optional Share atepdf action shares the product, not the user's current PDF or its name. The system result-share action remains separate. No address-book upload or auto-invites. Affiliate payouts, referral credits and partner codes require a later approved economics/abuse implementation; default launch has no referral reward.

## Error recovery that reduces support load
| Situation | Required response |
|---|---|
| Missing network before planning | Keep draft, explain AI needs internet; offer local shortcuts/compiled recipes |
| Network disappears after plan | Local execution can continue if resources are present; don't fabricate a cloud dependency |
| Unsupported operation or format | State limitation and viable local alternative; no paid claim |
| Compression target not met | Actual achieved size, quality trade-off and original preserved; do not claim success against target |
| Corrupt/password-protected input | Local preflight; secure local password control; no secrets in cloud prompt |
| Memory/storage limit | Safe cancel, release allowance, reduce supported batch; no hidden upload fallback |
| Local partial batch failure | Identify successful and failed members locally; retry failures safely without extra user debit |
| Save/share cancelled | Keep result ready; do not claim Saved or Delivered |
| Purchase pending/restore conflict | Retain local work, link correct recovery flow, no repeated charge request |
| App/tab restarted | Recover only persisted state, clearly request unavailable file access |
| Quota commit callback lost | Reconcile idempotent lease; avoid both double charging and unlimited unmetered planner traffic |

## Support and settings
A compact secondary panel contains My plan, Privacy and AI permission, Local storage, Help, Report a problem, Terms, app version and account actions. Report-a-problem initially offers reason codes and a diagnostic preview. Default diagnostics include app/OS versions, engine IDs, durations, resource buckets and opaque error codes only. Filenames, file data, page images, document text, paths, raw prompts, passwords and full receipts are excluded.

Sending an optional user-written support message is a separate intentional submission with a warning not to include sensitive content. Do not automatically attach the current document or screenshot. A case ID and self-service help article should handle most common problems; don't promise staffed 24/7 support as a solo founder.

Account deletion must be available in-app where accounts exist, with a clear web route where required. Explain which records are retained for legal/accounting duties, which are removed and how to cancel future billing; don't misstate an external store subscription as cancelled merely by deleting the app account. Follow the actual provider's deletion/cancellation sequence, retaining a minimal permitted billing reference if necessary. Local working-data deletion is separately selectable and never deletes user originals outside the app without explicit selection and confirmation.

## Packaging and future improvements
Ship activation, contextual offer, sandbox purchase/restore, plan management, account deletion and diagnostics before paid launch. Add recipes and cross-device linking before advertising them as Pro benefits. Advanced CRM, elaborate churn quizzes, expensive referral systems and push campaigns are later tests, not reasons to delay a genuine working product.
