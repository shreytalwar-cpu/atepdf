# ADR 0010 — Proposed protected Mac workspace storage (SHR-38)

**Status:** Proposed for Shrey's review; not approved or implemented.  **Source:** `main` at `1545d18e0f37e34f3682c308b25d55f545f97fca` (29 September 2026).  **Authority:** `PRODUCT_V1.md` STATE-01–07, PDF-07, PRIV-01–07 and OPEN-05; [SHR-38](https://linear.app/shrey-talwar/issue/SHR-38/decide-protected-local-storage-recovery-and-retention-policy), parent SHR-18 and the atePDF v1 Linear execution plan. SHR-34 (Mac support envelope) and SHR-91 (channel identities) remain open. This ADR recommends a contract; it does not assert a storage feature exists.

## Current-source evidence and threat boundary

`LocalFileStore` holds PDF bytes, metadata, original refs, committed result history and a numeric revision in memory. `JobController` validates and stages a result before an in-memory commit; `undo()` changes history but leaves prior bytes in its map. `App.tsx` keeps conversation entries, pending clarification, choices and save receipts in memory; composer draft state is not a durable workspace record. Some entries contain executable request/envelope data or pairing tokens and cannot be serialized as-is. Mac Catalyst import copies through `DocumentPicker` cache; inspection, previews and export use disposable cache files. Native code checks cache isolation and generated preview PNGs get restricted permissions; a file-protection attribute is conditional on the iOS compilation path and is not verified as Mac storage protection. The workspace has no durable private store, checkpoint, migration, retention or restore path. An exported copy belongs to the user and must never be treated as app-owned workspace data. The prototype audit describes the earlier memory-only snapshot; it is not evidence of current persistence.

The design protects against ordinary app crashes, partial writes, accidental replay, casual access to app files and accidental disclosure through caches or backups. It does not promise protection against a compromised logged-in process, forensic SSD erasure, third-party backup deletion, or restoration on another Mac without a separate recovery design.

## Recommendation and data placement

Use **one private, versioned workspace directory in Mac Catalyst Application Support**, found through Foundation's directory API, with immutable encrypted blob files and small encrypted checkpoint manifests. Keep the existing controller and PDF engines. Add a narrow persistence adapter at the validated commit boundary; do not create a second execution system, database, account, sync service or dependency. `Caches`/temporary directories remain disposable and cannot be needed for restore. Apple distinguishes durable Application Support from purgeable Caches/temporary storage and places Application Support inside the sandbox for sandboxed Mac apps ([Apple file-system guidance](https://developer.apple.com/documentation/foundation/using-the-file-system-effectively), [Application Support](https://developer.apple.com/documentation/foundation/url/applicationsupportdirectory)).

| Class | Durable representation and location |
| --- | --- |
| Conversation | Encrypted, typed display-history records in the manifest: role, safe text, timestamps/order, stable artifact references and non-executable outcome/receipt summaries. Exclude secret-bearing fields. Not a model transcript or unrestricted planner context. |
| Workspace/selection | Encrypted manifest: workspace ID, schema version, generation, revision/restore epoch, ordered original refs, committed result or collection refs, current selection/focus, one-Undo predecessor, and relevant non-secret parameters. Preserve input order. |
| Originals/results | Immutable, encrypted, individually authenticated PDF blobs in Application Support, addressed by opaque app refs. Store validated size/hash/inspection metadata in the manifest. Never overwrite an imported source or result blob. An imported workspace copy is distinct from its external source. |
| Draft | Only an explicitly safe, inert draft projection: non-secret text/parameters and selected refs. A draft is never a ready-to-run plan or approval. If safety cannot be established, omit it and restore the remaining workspace with a truthful notice. |
| Derived data | Persist only derived content actually needed for a committed result or approved workspace behavior, encrypted like document content. OCR/extracted text, analysis and previews are sensitive; regenerate disposable previews where possible. No generic plaintext cache for retained decrypted results. |
| Settings/receipts | Versioned retention preference and minimal non-secret privacy receipt metadata in the protected manifest. Receipts are audit/display facts, not reusable transfer authorization. Credentials and authentication tokens, when separately allowed, belong only in OS secure storage. |
| Temporary work | Picker copies, active staging, render/preview and export handoff files in isolated Caches/temporary roots with restrictive access, bounded lifetime and startup/orphan cleanup. Never index them as durable artifacts. External save/export destinations are outside the app's deletion and retention scope. |

**Never checkpoint:** document passwords, API keys, bearer/pairing codes, raw provider responses containing secrets, pending `PlannerRequest`/`Envelope`, executable confirmation callbacks, in-flight jobs, payment intents, network retry queues, reusable content-transfer grants, uncommitted transform output, or raw UI state. Recognized secrets in conversation must be removed/redacted before writing; this depends on SHR-71. Arbitrary free text can hide unrecognized secrets, so pattern matching cannot establish an absolute no-secrets guarantee. The user-visible handling of such text needs explicit approval rather than a false claim of perfect detection.

## Protection, backup and channels

Recommend a random per-workspace symmetric key in the macOS Keychain, accessible only to the app while the user is unlocked, and Apple CryptoKit AES-GCM for each blob and manifest. Authenticate format/version, workspace ID, ref, type and creation generation as associated data; use a fresh random nonce for every seal and record that creation generation for later manifests referencing the immutable blob. Restrict directory/file permissions; never log plaintext, keys, paths or document-derived content. The key is not in the manifest, preferences or repository. Keychain loss or denial must **lock recovery without creating an empty replacement over existing state**. Verify Keychain attributes and access groups on the actual approved Mac OS/channel matrix before implementation. Apple documents authenticated AES-GCM and Keychain accessibility ([CryptoKit](https://developer.apple.com/documentation/cryptokit/aes/gcm), [Keychain access](https://developer.apple.com/documentation/security/restricting-keychain-item-accessibility)).

Recommend **excluding the app-owned encrypted workspace from OS backup in v1**, with explicit disclosure that this supports relaunch/crash recovery on the same Mac, not device-loss or cross-Mac recovery. Disposable Caches are already outside normal backup. Reapply the exclusion after file replacement; Apple notes that replacement can reset the backup resource value ([backup exclusion key](https://developer.apple.com/documentation/foundation/urlresourcekey/isexcludedfrombackupkey)). This recommendation needs Shrey's approval. If backup/transfer recovery is required, the key-custody and recovery design must be decided before implementation; backing up ciphertext while keeping a non-migrating key is not a usable recovery plan. Do not silently place workspace data in iCloud or add sync.

Use the app's resolved private container rather than a hard-coded bundle-ID path. Mac App Store and direct builds must prove their final sandbox, bundle ID and Keychain identity/access-group behavior under SHR-91 before promising that one channel can open the other's data. Do not silently migrate or merge stores. External source paths/bookmarks are optional provenance only: the app-owned imported copy is the restore authority; any later external access must be revalidated and requested again if missing or revoked. Apple documents sandboxed user-selected files and explicit security-scoped bookmark access across launches ([Apple sandbox file access](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox)).

## Checkpoint, recovery and migration contract for SHR-39

1. Define a strict, bounded schema with an allowlisted serializer. Include `schemaVersion`, `workspaceID`, monotonically increasing `generation` and `revision`, original/result/collection refs and order, focus/selection, committed Undo predecessor, safe conversation records, safe draft and retention preference. Validate lengths, ref uniqueness, history/focus membership, blob types, sizes, hashes and schema before hydrating. Do not serialize `Entry` or `LocalFileStore` internals wholesale. Keep the planner's active projection bounded separately from durable history.
2. Keep blob files immutable. Write new encrypted blobs to a private staging area on the same volume, validate their authentication and underlying PDF/hash, then write and sync a complete encrypted manifest referencing them. Publish the new generation through an atomic same-volume replacement of a tiny head record; keep the preceding valid generation until the new one is verified. Sync files and directory metadata where supported, and fault-test each boundary. Do not rely on `Data.write(.atomic)` alone as a multi-file transaction. Apple's file replacement API is designed to avoid loss of the prior item ([FileManager replacement](https://developer.apple.com/documentation/foundation/filemanager/replaceitemat%28_%3Awithitemat%3Abackupitemname%3Aoptions%3A%29)).
3. The durable head switch is the commit point. Only after it succeeds may the controller publish a successful committed result or Undo to the UI. If storage fails, retain the last good checkpoint and report the failure without claiming the new work is durable; originals and user-saved files remain unchanged. Serialize all workspace-changing commits and clear/retention actions through one coordinator. Preserve current validation, stale-revision rejection, cancellation, independent output inspection and staged commit. A restored revision/epoch must invalidate every pre-relaunch executable token or stale action.
4. On startup, authenticate and validate the newest complete checkpoint and all referenced blobs; fall back only to the preceding **same deletion epoch** valid checkpoint. Ignore and later scavenge orphan staging/blobs. On corrupt/unknown newer schema, missing key, missing required artifact or unsafe migration, do not overwrite data or silently present a partial workspace; open a recoverable read-only/error state and explain the last valid state or required action. Missing optional external sources do not invalidate the app-owned copy. Reinspect actual PDFs as necessary before use, and recheck capabilities and file refs before any new job.
5. Migrations are explicit, sequential and tested from each shipped schema. Write a new generation rather than mutating the old one, retain rollback until verified, and reject future/unknown schema without downgrade writes. Include a one-time empty-memory-store-to-first-checkpoint path; no prototype snapshot migration exists because no durable workspace exists today.
6. Restore only inert conversation/result state. Do not resume a planner call, paid request, transfer, confirmation, clarification action or PDF job. Clear in-flight flags and pending execution data. Prior consent receipts can explain what happened, but a transfer after restart requires a fresh operation-specific grant bound to current content revision, payload, recipients and purpose; revalidate credentials and file access. Do not present stale quality-change confirmation as active.

**Deletion/retention:** SHR-40 implements only Shrey-approved default and options. Recommend a persistent default (“keep until I delete”) because relaunch restore is a v1 promise, plus user-selectable finite retention periods and an explicitly chosen ephemeral mode only if approved; this ADR does **not** set durations. Explain the effects on chat, imported copies, results, current/Undo state, derived content, previews and diagnostics before applying a choice. Show app-owned storage usage; allow clear/delete regardless of AI or allowance. Expiry/deletion must coordinate with active jobs and never silently remove the current/Undo state before the approved policy says so. Clear must first publish a durable deletion epoch/tombstone that forbids fallback to pre-clear generations; then remove app-owned blobs, stale manifests, caches and the retired workspace key, retrying interrupted cleanup on launch. A corrupt tombstone fails closed. Never traverse external source/export locations. State plainly that deletion cannot erase user-saved copies, system/third-party backups or forensic remnants.

**Decrypted PDFs:** Unlocking is not implemented in this task. For a future approved Unlock PDF workflow, the unlocked result is a new sensitive immutable artifact only if the user chooses to retain it under the approved policy; encrypt it in Application Support and disclose that retention. A plaintext working copy may exist only in a private temporary root for the operation, must be removed on completion/cancel/startup and excluded from backup; no password is retained by default. If secure temporary handling cannot be proven, fail closed rather than leave a generic plaintext cache. Exporting an unlocked copy requires a separate explicit save and remains the user's file.

## Resource implications and alternatives

Individual encrypted blobs avoid rewriting every PDF on each chat change, but retained history consumes disk and encryption/inspection add CPU, I/O and transient memory. Stage one bounded artifact at a time where possible; account for duplicate imported/result bytes, the previous checkpoint, and temporary copies before accepting work. Measure limits on the approved Mac matrix (SHR-34); do not invent a device-size cutoff. Cache eviction must never remove a committed artifact or promised Undo predecessor.

Flat versioned files are the simplest fit for a single v1 workspace and current `LocalFileStore` semantics. SQLite would help a large searchable library or concurrent writers, neither approved; it still would not solve PDF blob protection, key custody or external-file permissions. `UserDefaults` is unsuitable for PDF bytes/transactional history. Plain JSON/PDF files in Application Support are easier to inspect but do not satisfy the recommended at-rest protection. Caches-only storage cannot promise relaunch restore. Security-scoped links to external originals would make restore depend on revocable access and moved files. Cloud/remote storage is outside v1.

## Approval gates and verification owed by later issues

**Shrey must approve before SHR-39/40 treats this as policy:** (a) app-managed encryption/Keychain model and the loss-of-key behavior; (b) backup exclusion and lack of cross-device recovery, or an alternative recoverable-backup plan; (c) retention default, exact finite choices/durations, whether ephemeral mode exists, and deletion explanation; (d) what conversation/draft text is eligible to persist given unrecognized-secret risk; (e) whether unlocked results are retained by default or only by explicit choice. SHR-34 must settle the Mac matrix and SHR-91 must settle channel identities/access before channel portability is claimed. Until approval, this remains a proposed ADR and dependent implementation must not assume the open values.

SHR-71's secret-exclusion behavior is a prerequisite for safe conversation persistence; SHR-39 already lists it as a blocker. The existing `LocalFileStore` retained-byte behavior and live cache cleanup need implementation and measurement in their assigned issues, not in SHR-38. No tests or runtime behavior changed here.
