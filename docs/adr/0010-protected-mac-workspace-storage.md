# ADR 0010 — Protected Mac workspace storage (SHR-38)

**Status:** Owner policy approved for SHR-38 on 29 September 2026; design in review, not implemented.  **Source:** `main` at `1545d18e0f37e34f3682c308b25d55f545f97fca` (29 September 2026).  **Authority:** `PRODUCT_V1.md` STATE-01–07, PDF-07, PRIV-01–07 and OPEN-05; [SHR-38](https://linear.app/shrey-talwar/issue/SHR-38/decide-protected-local-storage-recovery-and-retention-policy), parent SHR-18, the atePDF v1 Linear execution plan and Shrey's owner decisions in this task. SHR-34 (Mac support envelope) and SHR-91 (channel identities) remain open. This ADR is an implementation contract, not a claim that persistence exists.

## Current-source evidence and threat boundary

`LocalFileStore` holds PDF bytes, metadata, original refs, committed result history and a numeric revision in memory. `JobController` validates and stages a result before an in-memory commit; `undo()` changes history but leaves prior bytes in its map. `App.tsx` keeps conversation entries, pending clarification, choices and save receipts in memory; composer draft state is not a durable workspace record. Some entries contain executable request/envelope data or pairing tokens and cannot be serialized as-is. Mac Catalyst import copies through `DocumentPicker` cache; inspection, previews and export use disposable cache files. Native code checks cache isolation and generated preview PNGs get restricted permissions; a file-protection attribute is conditional on the iOS compilation path and is not verified as Mac storage protection. The workspace has no durable private store, checkpoint, migration, retention or restore path. An exported copy belongs to the user and must never be treated as app-owned workspace data. The prototype audit describes the earlier memory-only snapshot; it is not evidence of current persistence.

The design protects against ordinary app crashes, partial writes, accidental replay, casual access to app files and accidental disclosure through caches or backups. It does not promise protection against a compromised logged-in process, forensic SSD erasure, third-party backup deletion, or restoration on another Mac without a separate recovery design.

## Recommendation and data placement

Use **one private, versioned workspace directory in Mac Catalyst Application Support**, found through Foundation's directory API, with immutable encrypted blob files and small encrypted checkpoint manifests. Keep the existing controller and PDF engines. Add a narrow persistence adapter at the validated commit boundary; do not create a second execution system, database, account, sync service or dependency. `Caches`/temporary directories remain disposable and cannot be needed for restore. Apple distinguishes durable Application Support from purgeable Caches/temporary storage and places Application Support inside the sandbox for sandboxed Mac apps ([Apple file-system guidance](https://developer.apple.com/documentation/foundation/using-the-file-system-effectively), [Application Support](https://developer.apple.com/documentation/foundation/url/applicationsupportdirectory)).

| Class | Durable representation and location |
| --- | --- |
| Conversation | Encrypted, typed display-history records in the manifest: role, text after recognized-secret exclusion, timestamps/order, stable artifact references and non-executable outcome/receipt summaries. Ordinary chat may survive relaunch. Not a model transcript or unrestricted planner context. |
| Workspace/selection | Encrypted manifest: workspace ID, schema version, generation, revision/restore epoch, ordered original refs, committed result or collection refs, current selection/focus, one-Undo predecessor, and relevant non-secret parameters. Preserve input order. |
| Originals/results | Immutable, encrypted, individually authenticated PDF blobs in Application Support, addressed by opaque app refs. Store validated size/hash/inspection metadata in the manifest. Never overwrite an imported source or result blob. An imported workspace copy is distinct from its external source. |
| Draft | Encrypted ordinary draft text/parameters and selected refs after recognized-secret exclusion. A draft is inert: never a ready-to-run plan, payment, transfer or approval. Dedicated secret-field values and secure handles are excluded. |
| Derived data | Persist only derived content actually needed for a committed result or approved workspace behavior, encrypted like document content. OCR/extracted text, analysis and previews are sensitive; regenerate disposable previews where possible. No generic plaintext cache for retained decrypted results. |
| Settings/receipts | Versioned retention preference and minimal non-secret privacy receipt metadata in the protected manifest. Receipts are audit/display facts, not reusable transfer authorization. Credentials and authentication tokens, when separately allowed, belong only in OS secure storage. |
| Temporary work | Picker copies, active staging, render/preview and export handoff files in isolated Caches/temporary roots with restrictive access, bounded lifetime and startup/orphan cleanup. Never index them as durable artifacts. External save/export destinations are outside the app's deletion and retention scope. |

**Never checkpoint:** document passwords, API keys, bearer/pairing codes, dedicated secure-field values or handles, raw provider responses containing secrets, pending `PlannerRequest`/`Envelope`, executable confirmation callbacks, in-flight jobs, payment intents, network retry queues, reusable content-transfer grants, uncommitted transform output, or raw UI state. SHR-71's recognized-secret exclusion must run **before** a conversation/draft checkpoint; a later Clear action is not a substitute. Arbitrary free text can hide unrecognized sensitive data, so neither the architecture nor the product may claim perfect detection. Ordinary retained chat/drafts are encrypted local data, not automatically safe to send to a model.

## Protection, backup and channels

Use a random per-workspace symmetric key in the device-local macOS Keychain and Apple CryptoKit AES-GCM for each blob and manifest. On macOS use the Data Protection Keychain (`kSecUseDataProtectionKeychain=true`), a suitable `ThisDeviceOnly` unlocked accessibility class and `kSecAttrSynchronizable=false`; verify these exact attributes and access groups on the approved Mac/channel builds. Apple specifies the Data Protection Keychain for iOS-style accessibility without iCloud synchronization ([Data Protection Keychain](https://developer.apple.com/documentation/security/ksecusedataprotectionkeychain), [synchronization attribute](https://developer.apple.com/documentation/security/ksecattrsynchronizable), [Keychain access](https://developer.apple.com/documentation/security/restricting-keychain-item-accessibility)). Authenticate format/version, workspace ID, ref, type and creation generation as associated data; use a fresh random nonce for every seal and record that creation generation for later manifests referencing the immutable blob ([CryptoKit AES-GCM](https://developer.apple.com/documentation/cryptokit/aes/gcm)). Restrict directory/file permissions; never log plaintext, keys, paths or document-derived content. The key is not in the manifest, preferences or repository. If it is temporarily unavailable, offer retry after unlock. If irrecoverably lost, **leave encrypted state intact and explain that the workspace cannot be recovered**; do not weaken encryption, invent cloud recovery or silently replace the workspace. User-exported files remain accessible independently.

The private encrypted workspace is **not a document backup system**. Exclude its entire Application Support workspace directory—including manifests, imported/result PDF payloads and sensitive derived data—from OS app-data backup where macOS supports the exclusion; keeping only metadata in a backup would produce an unrestorable partial workspace. Reapply and verify the exclusion after replacement because file operations can reset it ([Apple backup exclusion](https://developer.apple.com/documentation/foundation/urlresourcekey/isexcludedfrombackupkey), [file-system guidance](https://developer.apple.com/documentation/foundation/using-the-file-system-effectively)). Caches/temporary files are disposable and normally not backed up, but cleanup remains required. OS flags cannot control third-party copying or a user's chosen external export destination; do not promise universal backup exclusion. This design provides same-installation relaunch/crash recovery, not device-loss/cross-Mac recovery. No iCloud sync or cloud key recovery is added. Explicitly saved/exported files follow the user's chosen destination and backup behavior.

Use the app's resolved private container rather than a hard-coded bundle-ID path. Mac App Store and direct builds must prove their final sandbox, bundle ID and Keychain identity/access-group behavior under SHR-91 before promising that one channel can open the other's data. Do not silently migrate or merge stores. External source paths/bookmarks are optional provenance only: the app-owned imported copy is the restore authority; any later external access must be revalidated and requested again if missing or revoked. Apple documents sandboxed user-selected files and explicit security-scoped bookmark access across launches ([Apple sandbox file access](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox)).

## Checkpoint, recovery and migration contract for SHR-39

1. Define a strict, bounded schema with an allowlisted serializer. Include `schemaVersion`, `workspaceID`, monotonically increasing `generation` and `revision`, deletion epoch, original/result/collection refs and order, focus/selection, committed Undo predecessor, redacted conversation records, inert draft, retention mode and last user workspace activity time. Validate lengths, ref uniqueness, history/focus membership, blob types, sizes, hashes and schema before hydrating. Do not serialize `Entry` or `LocalFileStore` internals wholesale. Keep the planner's active projection bounded separately from durable history. A committed chat change and meaningful workspace-state change require a checkpoint; draft changes may be coalesced, with only the last completed checkpoint promised after a crash.
2. Keep blob files immutable. Write new encrypted blobs to a private staging area on the same volume, validate their authentication and underlying PDF/hash, then write and sync a complete encrypted manifest referencing them. Publish the new generation through an atomic same-volume replacement of a tiny head record; keep the preceding valid generation until the new one is verified. Sync files and directory metadata where supported, and fault-test each boundary. Do not rely on `Data.write(.atomic)` alone as a multi-file transaction. Apple's file replacement API is designed to avoid loss of the prior item ([FileManager replacement](https://developer.apple.com/documentation/foundation/filemanager/replaceitemat%28_%3Awithitemat%3Abackupitemname%3Aoptions%3A%29)).
3. The durable head switch is the commit point. Only after it succeeds may the controller publish a successful committed result or Undo to the UI. If storage fails, retain the last good checkpoint and report the failure without claiming the new work is durable; originals and user-saved files remain unchanged. Serialize all workspace-changing commits and clear/retention actions through one coordinator. Preserve current validation, stale-revision rejection, cancellation, independent output inspection and staged commit. A restored revision/epoch must invalidate every pre-relaunch executable token or stale action.
4. On startup, authenticate and validate the newest complete checkpoint and all referenced blobs; fall back only to the preceding **same deletion epoch** valid checkpoint. Ignore and later scavenge orphan staging/blobs. On corrupt/unknown newer schema, missing key, missing required artifact or unsafe migration, do not overwrite data or silently present a partial workspace; open a recoverable read-only/error state and explain the last valid state or required action. Never fall back across a clear/expiry epoch. Missing optional external sources do not invalidate the app-owned copy. Reinspect actual PDFs as necessary before use, and recheck capabilities and file refs before any new job.
5. Migrations are explicit, sequential and tested from each shipped schema. Write a new generation rather than mutating the old one, retain rollback until verified, and reject future/unknown schema without downgrade writes. Include a one-time empty-memory-store-to-first-checkpoint path; no prototype snapshot migration exists because no durable workspace exists today.
6. Restore only inert conversation/result state. Do not resume a planner call, paid request, transfer, confirmation, clarification action or PDF job. Clear in-flight flags and pending execution data. Prior consent receipts can explain what happened, but a transfer after restart requires a fresh operation-specific grant bound to current content revision, payload, recipients and purpose; revalidate credentials and file access. Do not present stale quality-change confirmation as active.

**Approved retention:** Default **Keep until I delete it**, with no silent age expiry. The other v1 modes are **30 days**, **7 days** and **Delete on close**. For the finite modes, treat this single v1 workspace as one unit, measuring from the last user action that changes retained workspace state (chat, draft, import, selection or committed PDF result); passive launch/viewing does not renew it. Expire the whole workspace when due, checking on launch, foreground return and before another action. The app cannot guarantee deletion while it is not running. Do not expire just one result while keeping broken references to it. Changing to a shorter mode checks the existing age immediately. A backwards clock or invalid timestamp must fail closed to a review/error state rather than silently extend retention. UI wording and presentation remain SHR-40 work.

**Delete on close** means the last workspace window closes or the app quits, whichever happens first; minimizing or backgrounding is not close. Selecting this mode immediately clears any previously durable workspace and stops writing durable chat/PDF/draft checkpoints for that session, so a force-quit or crash cannot resurrect the session. Keep active state only in memory and clean private temporary copies on close/startup. This is an explicit loss-of-relaunch choice, not the default. If Mac window/session semantics differ in the eventual approved channel build, SHR-40 must preserve the no-replay/no-resurrection rule and put any changed user-visible interpretation back to Shrey for approval.

**Clear History/Workspace at any time:** stop/cancel and join active work first; refuse any late callback from re-committing. Atomically publish a new empty deletion epoch (with a new key if a new workspace is opened) **before** garbage-collecting old data; a crash must never restore an older pre-clear generation. Remove all atePDF-managed workspace chat, draft, imported copies, generated results, original/result refs and history, previews, caches, document-understanding data, temporary/decrypted working copies, metadata, the stored retention selection and the retired key. Retry interrupted physical cleanup without reopening cleared data. A new workspace uses the approved Keep until I delete it default unless the user selects another mode. Clear remains available without AI or allowance. Never traverse, modify or delete external source paths or user-selected save/export destinations. Explain that this is app-controlled deletion, not forensic erasure or removal from third-party backups. This workspace action does not silently alter separate account, purchase or provider credentials; those are governed by their own controls.

**Decrypted PDFs:** Unlocking is not implemented in this task. A future unlocked result may be retained **only if required to restore the active workspace/current result**; it is a sensitive immutable encrypted blob in Application Support and follows the same retention/Clear policy. Do not keep an additional long-lived plaintext copy or retain the password by default. A plaintext working copy may exist only in a private temporary root for the operation, must be removed as soon as reasonably possible after completion/cancel and again on startup, and must be excluded from backup. If secure temporary handling cannot be proven, fail closed rather than leave a generic plaintext cache. A user-exported unlocked PDF is outside the workspace lifecycle and remains the user's file.

## Resource implications and alternatives

Individual encrypted blobs avoid rewriting every PDF on each chat change, but retained history consumes disk and encryption/inspection add CPU, I/O and transient memory. Stage one bounded artifact at a time where possible; account for duplicate imported/result bytes, the previous checkpoint, and temporary copies before accepting work. Measure limits on the approved Mac matrix (SHR-34); do not invent a device-size cutoff. Cache eviction must never remove a committed artifact or promised Undo predecessor.

Flat versioned files are the simplest fit for a single v1 workspace and current `LocalFileStore` semantics. SQLite would help a large searchable library or concurrent writers, neither approved; it still would not solve PDF blob protection, key custody or external-file permissions. `UserDefaults` is unsuitable for PDF bytes/transactional history. Plain JSON/PDF files in Application Support are easier to inspect but do not satisfy the recommended at-rest protection. Caches-only storage cannot promise relaunch restore. Security-scoped links to external originals would make restore depend on revocable access and moved files. Cloud/remote storage is outside v1.
