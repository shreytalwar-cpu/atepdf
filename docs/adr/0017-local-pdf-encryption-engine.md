## 1. Required envelope and evidence vocabulary

- Local Protect and known-password Unlock; no cloud fallback, guessing, cracking, production keys or customer PDFs.
- Mac Catalyst on macOS 14+, arm64 and x86_64 Universal target. Intel public support remains conditional on real Intel runtime acceptance under ADR 0011. Preserve the existing app architecture.
- Same encryption profile for Mac App Store, direct download and intended Setapp channel. Channel approval, signing, storage identity and commercial terms remain SHR-91 work.
- Immutable source; complete schema/semantic/capability/ref/revision admission; staged output, cancellation, independent inspection, durable promotion and Undo. No engine-driven relaxation of content/resource admission.
- Preserve admitted pages, geometry, drawing/text/image content and supported structures; an encryption rewrite is not flattening, rasterization, metadata removal or signature preservation.
- Raw document passwords remain native and transient. Device-local workspace protection and PDF password protection are separate mechanisms.

**Proven** means a recorded local observation on the named input/build. **Compile-compatible** means a named binary compiled/linked for that platform, without a runtime claim. **Documented** means upstream API/source/policy evidence. **Unverified** means a required check has not run. These labels apply separately to the engine, reader, app and channel.

## 4. Approved v1 output profile (ENC-2/3)

| Parameter | Approved requirement |
|---|---|
| Encryption | **AES-256**, Standard password security handler `/Filter /Standard`, **`/V 5`, `/R 6`, `/Length 256`**, crypt filter **`/CFM /AESV3`** for strings and streams; document-open authentication. No R5, AES-128 or RC4 Protect output. |
| PDF version | Minimum **PDF 1.7 with extension level 8**; retain a higher input version where required. Do not force a lower version. Explicitly set/inspect the version and catalog extension, rather than relying on old header comments mentioning extension 3. [Current QPDF encryption CLI documentation](https://qpdf.readthedocs.io/en/stable/cli.html#encryption). |
| User/open password | Dedicated secure local input; nonempty. Use the approved initial, explicit printable-ASCII envelope of **0x20–0x7E (space allowed), 1–127 bytes**, without NUL, trimming or case changes. Encourage a strong passphrase; AES does not make a weak password strong. This is an approved interoperability restriction, not a claim QPDF lacks Unicode support. |
| Owner password | Generate a fresh internal **256-bit random** value per output using the OS CSPRNG, encode as 64 ASCII hex characters, ensure it differs from the user password, and discard after verification. Never blank or equal; no stored recovery password/key escrow. This is internal security plumbing, not a user-facing password-generation feature. |
| Permissions | All defined operations allowed after correct opening password: full printing, copy/extract, assembly, annotation/forms, form fill, modification and accessibility. Effective `/P` permission mask fully permissive (normally signed **-4**, equivalently unsigned 4294967292). Reserved bits must be valid; verify semantic flags. No v1 DRM/restriction UI. |
| Metadata | **EncryptMetadata=true**, including XMP metadata streams and ordinary document-info strings under the security handler. Preserve admitted metadata; Protect does not mean Remove Metadata. Cleartext metadata option prohibited. Trailer/security dictionaries, xref, sizes and other structural information remain exposed; encryption is not filename hiding or authenticated tamper evidence. |
| Randomness | Use upstream production key/salt/IV generation and the selected crypto provider. Never static AES IV/ID or deterministic encryption for output. Ciphertext equality is not a test oracle. |

R6 is QPDF's nondeprecated handler recommendation; an empty owner password can allow opening without the chosen user password. [Handler and password semantics](https://qpdf.readthedocs.io/en/stable/encryption.html). QPDF's library takes password bytes; its inspected pinned source truncates V5 passwords at 127 bytes. Enforce the output bound before the engine to prevent silent truncation. Unicode creation and known-password input require a separately tested encoding/normalization contract before expanding the initial ASCII envelope. [Pinned encryption source](https://github.com/qpdf/qpdf/blob/v12.4.2/libqpdf/QPDF_encryption.cc).

**Interoperability target:** current Preview and Adobe Acrobat/Reader on the supported Mac envelope, plus PDF.js and Poppler as independent automation readers. Preview password support is [documented by Apple](https://support.apple.com/guide/preview/password-protect-a-pdf-prvw587dd90f/mac); this is not an R6 output acceptance certificate. Actual reader versions must be recorded in SHR-60/61. Very old readers are outside the approved profile; never downgrade silently to make them open a result.

## 5. Input authentication, restrictions and failure policy (ENC-3/4)

Approved initial Unlock policy envelope: unsigned **Standard-handler AES-128 V4/R4 (AESV2)** and **AES-256 V5/R5 or R6 (AESV3)** with tested document-open string/stream filters and printable-ASCII known passwords (0x20–0x7E, space allowed; secure input 1–127 bytes, with the existing handler-specific R4 ≤32-byte bound and R5/6 ≤127-byte bound). R5 is accepted only as input, not emitted. These are **approved policy/documented library capabilities**, not tested QPDF support claims; release support remains conditional on the missing proof. Initial acceptance requires the missing R4/R5 and restricted fixtures. R4/AESV2 password authentication requires RC4 internally: statically include the OpenSSL legacy provider in the signed bundle, with its notices and measured size; this does not admit RC4-only PDFs. The adapter must classify RC4-only input from `/Encrypt` and its crypt filters **before authentication** and refuse it. RC4 R2/R3/R4, V3, certificate/public-key handlers, proprietary DRM, mixed/unknown filters, attachment-only encryption and unproved encodings fail with unsupported input; expand only through explicit evidence and policy review.

| Input/event | Required local behavior |
|---|---|
| Non-ASCII password on Protect or Unlock | Refuse specifically in the secure local control: “Use a password with printable ASCII characters (spaces are allowed). This version can’t use non-ASCII passwords.” Do not trim, normalize, truncate or send the value to chat/model context. |
| Empty user password with fully permissive `/P` | Classify that the document opens without a password; accept the ordinary empty-user authentication check without guessing. Create an independently verified unlocked copy only on the explicit Unlock request, with unchanged encrypted original and the same retention/export disclosure. This is an encrypted-input exception, not permission to create an empty Protect password. |
| Wrong password | Classify typed engine authentication failure as wrong-password; no partial import/result, promotion or automatic retry. Destroy attempt state and handle; allow only another user-supplied secure attempt. Never report every parse error as wrong-password. |
| Nonempty user/open password; no effective operation restrictions | Correct user or owner authentication may create a separately verified decrypted result. Explain retention/export consequences. Preserve original encrypted bytes. |
| Restricted permissions, including a PDF that opens automatically with empty user password | Opening is not authority to strip restrictions. Require the **known owner password**, prove owner authentication, and obtain explicit local confirmation that the unlocked output removes restrictions. A checkbox claiming ownership cannot replace owner authentication. |
| Restricted PDF authenticated only as user | Read-only access is possible in the engine, but refuse Unlock output and restricted downstream processing in v1. Explain that the owner password is needed. Do not let QPDF's permissive behavior silently bypass policy. |
| Unencrypted PDF | Unlock reports already unprotected; no false encryption-removal claim. Normal tools still obey their admission checks. |
| Unsupported algorithm/handler/encoding | Refuse locally with an actionable supported-profile explanation; keep source unchanged. No reader-driven fallback, weak Protect downgrade or cloud conversion. |
| Malformed encrypted PDF or invalid permissions/crypto dictionary | Fail closed, disable recovery where available, reject warnings/ambiguous status, release staged bytes/handles. Do not guess missing security parameters or salvage a partially decrypted document. |
| Signed + encrypted | A password may authenticate for **read-only classification**; no transformation or plaintext output if signed/certified indicators are found, or signature status cannot be safely established. |
| Cancel, stale ref/revision, reset, resource/storage error | No commit; retain prior valid result and immutable original. Revoke handles, join actual engine work, discard staged output and complete/retry required cleanup. |

Permission flags are **reader-enforced preferences, not strong DRM**. QPDF does not itself police restrictions; the adapter must gate writes using authenticated owner/user status and effective permissions. Never expose key-based opening, password recovery, the separate QPDF `--remove-restrictions` operation, speculative encodings or password guesses. Encryption removal is allowed only under the explicit credential/restriction policy above. The ordinary empty-password opening check for an already-opening PDF is not a guessing loop.

## 6. Digitally signed PDF policy (ENC-5)

**Approved policy: refuse Protect, Unlock and re-encryption of digitally signed or certified PDFs in v1.** Preserve and permit access to the original; explain that rewriting can invalidate signatures and that atePDF has no signature-preserving transform workflow. Do not present a retained signature image/field as valid cryptographic evidence. Signature creation/editing is v2 under PRODUCT_V1.

Inspect the authenticated object graph, including inherited `/FT /Sig` fields, signature dictionaries/values, `/ByteRange`, `/Contents`, catalog `/Perms`/DocMDP and certification references. Per merged [ADR 0013 CPDF-4](0013-first-complex-pdf-preservation-slice.md), explicitly refuse **unsigned and empty `/FT /Sig` fields** as well as signed/certified inputs. Conservatively refuse ambiguous or unsupported signature structures. Do not use raw-byte substring searches as the security gate, or claim certificate/trust validation. No network certificate lookup is needed to enforce refusal. QPDF's restriction-removal option explicitly invalidates signatures; it must never be part of this interface. [QPDF signed-file warning](https://qpdf.readthedocs.io/en/stable/cli.html#option-remove-restrictions).

The read-only authentication probe is not implementation of this detector. Later proof needs a genuinely signed synthetic input and a signed+encrypted input, including certification/incremental revisions; a decorative signature or empty dictionary does not prove this policy.

## 8. Password interface contract for SHR-53

The following is an approved interface contract, **not new code or a model tool schema**:

1. Dedicated masked **native secure input** owns the raw value. Ordinary React/JS state, chat, planner requests, model/provider context, transcript, clipboard receipts, analytics, logs and persistence never receive it. Recognized-secret exclusion in `privacy.ts` remains defense-in-depth, not the primary secure-input mechanism.
2. Return an unpredictable **opaque local handle** bound to workspace/epoch, document ref and byte revision, job, purpose (open/user/owner), scope and expiry. Handles are not executable authority by themselves. Resolve only inside the native local engine; only local state may hold them. A hosted model may request that local secure input is needed, but must not receive a raw secret, any secure handle or its identifier (ADR 0012 N-01). Existing complete-plan validation remains mandatory.
3. Native adapter accepts approved input ref, job/revision binding, opaque handle(s), fixed profile ID, cancellation context and staged destination capability. No arbitrary paths, crypto keys, algorithms, permission bypass flags or command/job JSON. Resolve a short-lived buffer only immediately around authentication/write/independent verification; bounded re-use within that same job is required for output verification.
4. QPDF API mapping to prove: input `processMemoryFile()` or caller-owned file input; inspect encryption method and `ownerPasswordMatched()`/`userPasswordMatched()`; output R6 parameters for Protect and preserve-encryption=false for Unlock. Translate to typed statuses: wrong-password, non-ASCII-password-refused, unsupported-profile, owner-password-required, signed-input-refused, malformed-input, expired-handle, cancelled, resource/storage/verification failure. Never propagate raw upstream messages or filenames. [Pinned QPDF input/status API](https://github.com/qpdf/qpdf/blob/v12.4.2/include/qpdf/QPDF.hh), [writer API](https://github.com/qpdf/qpdf/blob/v12.4.2/include/qpdf/QPDFWriter.hh).
5. Success, wrong-password attempt, verification failure, cancel, reset, expiry, bridge teardown and app quit revoke the handle. Cancellation must first make promotion impossible, then join the engine call before destroying buffers it still uses. Clear the field and owned mutable buffers; destroy QPDF/reader/crypto objects and staging. A late callback cannot publish or reauthorize work; restart requires fresh secure input.
6. Use a non-optimizable OS memory-clearing primitive for owned buffers. ## 9. Unlock output storage (SHR-38 contract)

Decrypted working/output copies are permitted **only within ADR 0010's existing approval**. Prefer bounded native memory for active data. If a file is unavoidable for inspection/export, use an isolated app-private operation directory in Caches/temporary storage, restrictive directory/file permissions, backup exclusion, no symlink traversal, and a tracked lifetime. Delete on completion/cancel/reset and scavenge orphans on startup; fail closed if secure placement or cleanup cannot be established. Generic caches and long-lived extra plaintext copies are prohibited.

Retain an unlocked immutable result only when needed to restore the active workspace/current result, sealed by the reviewed CryptoKit AES-GCM vault in private Application Support under the device-local nonsynchronizing Keychain key. Retained derived data/previews receive the same protection or are regenerated. Never use the document password as the workspace key or checkpoint it. This is encryption **at rest** of an otherwise unlocked PDF, not a claim that the exported PDF requires a password.

Apply the approved default **Keep until I delete it**, or the selected **30 days / 7 days / Delete when atePDF quits**, with the same workspace activity/expiry/deletion epoch and crash-safe cleanup behavior. Window close does not mean app quit. Clear cancels/joins work, prevents resurrection and removes app-owned decrypted/temp/derived copies; interrupted cleanup stays pending and is retried. External originals and deliberately exported unlocked PDFs survive Clear/expiry and follow the user's destination/backups. Disclose that export removes the opening-password protection. No cloud sync, key escrow, document-password recovery or forensic-erasure guarantee.

Source implementations and helper tests do not establish final channel Keychain, backup or plaintext-cleanup acceptance.
