Audit date: 29 September 2026. Frozen source: **`5a6c0c542603cdb2a72bcdb2a91958ef3b6f12ab`**. HEAD matched this commit and source was clean at intake. This is a read-only source/import/route audit. No installs, builds, tests, app launches, browser probes, paid calls, UI changes, or new screenshots were performed. Only this document was written.

The prototype has one reachable application UI: the Expo/React Native conversation with assistant-ui. It implements a bounded local PDF workflow and optional planning. It is not yet a general PDF utility, persistent chat product, broadly verified browser/mobile product, or released service. ## Interpretation and evidence boundary

These are capability statuses, not release acceptance.

**KEEP / REFACTOR / REPLACE / REMOVE / UNKNOWN** below are subsystem dispositions for later decisions, not authorization to edit. No selected framework needs replacement based on this audit. ## Responsive, accessibility, errors and performance

**Strengths to preserve.** The active UI has a named main region, button labels, result headings, disabled state, visible keyboard focus, readable result facts, 44-unit minimum controls, safe-area padding, large-text shortcut scrolling, keyboard-aware native secondary controls, and reduced-motion-aware activity. Web preview returns focus on explicit Close. Progress announcements distinguish phases from per-page detail. Existing geometry tests cover 320/390/768/1440-class layouts, short windows and 200% root text in Chrome; they are valuable bounded evidence, not WCAG or user-study certification.

**Accessibility limits.** The PDF itself is raster-only, labelled by page number; no semantic text alternative or searchable layer is exposed to assistive technology. Source role/live-region declarations alone do not establish announcement order, duplicate-announcement absence, focus-trap behavior, rotor/navigation usability or accessible system dialogs. Existing VoiceOver/physical-device gates remain open. Native preview focus return is not explicit in its Close callback as it is on web. Unused template edit controls have 32-unit sizing, but they are capability-gated off and should not be misreported as current reachable target failures. Dark-mode tokens in template classes do not establish dark-mode support: [app.json:8](/Users/shrey/Documents/ChatGPT/atepdf/apps/universal/app.json:8) explicitly selects light appearance.

**Browser compatibility.** Web adapters assume Worker/module workers, PDF.js/WASM, canvas/createImageBitmap/OffscreenCanvas, cryptographic UUID/SHA-256, structuredClone, ResizeObserver, modern array methods, and AbortSignal timeout/any. The web polyfill file contains only a comment. These are source requirements, not an audited minimum-version matrix. `showSaveFilePicker` has a download fallback; picker `cancel` lacks a secondary focus-based settlement path. The actual Expo HTML lacks the Next layout's `interactiveWidget:'resizes-content'` viewport declaration. The live web root uses fixed/full-height layout with nested scroll containers; no physical mobile-keyboard result can be inferred from the unused legacy Workspace's visualViewport listener. Fonts/engines use root-relative URLs; subpath hosting is not established.

**Error behavior.** Invalid page ranges, unsupported PDFs, cancellation, stale/invalid plans, no useful compression, preview errors, save cancellation, and disconnected AI have reachable messages with preserved output. Admission intentionally rejects annotations/links, forms, tagged structures, outlines/names/actions and unsupported drawing content; “PDF support” must remain qualified. Errors do not offer a general Retry mechanism; a failed native preview requires navigation/reopening. No active app error-boundary/recovery screen was found. Native bridge gating keeps unavailable builds from processing, but it is not an engine-conformance test.

**Performance.** Historical candidate10 entry is 2,240,317 bytes; actual gzip body is 486,133. The preserved same-export profile observed first control at 12.320s identity versus 3.342s gzip with 4× CPU/1.6Mbps, and 156ms versus 183ms on ordinary loopback. One pair per profile is not a distribution or production metric. Complete welcome artwork took 7.131s in the separate constrained capture; its approximately 688 KB paper asset remains unchanged. PDF.js/Tesseract are dynamically imported; OCR assets are local and lazy. Beta gzip touches public JS/CSS only, with no new cache; Next/preview-server behavior must be assessed separately.

Session growth remains a practical limit: original/result byte snapshots and inspection text persist until clear, and `store.list` clones all metadata repeatedly. Visible messages also search the entries list to find their local extras. FlatList limits mounted rows but does not release the backing document history. Browser workers receive cloned request bytes without transfer lists; native writer transforms run in JavaScript with cooperative checkpoints and synchronous parsing portions. No measured ceiling or physical-memory-pressure response is established. These are reasons to measure representative tasks, not to invent an arbitrary PDF size cap.
