# PDF engines, local execution and testing audit

Audit date: 2026-09-29. Frozen source: `5a6c0c542603cdb2a72bcdb2a91958ef3b6f12ab`; annotated `prototype-v0` was read and its peeled commit matches that SHA. Repository root: `/Users/shrey/Documents/ChatGPT/atepdf`. All source anchors below are relative to that root and use one-based lines.

This was a source review and a read of existing evidence. **No application, build, test, simulator, installer, PDF processor or paid request was run during this audit. No application or test source was changed.** This document is the only audit output owned by this reviewer. The old Attenlo checkout and credentials were not accessed. PDFKit and iOS audit guidance informed the review; the owner’s freeze superseded their usual build steps.

## Decision

**KEEP the local-first separation and existing engines; REFACTOR the resource policy, preservation validation and long-session manifest boundary before widening the supported PDF corpus.** The code implements a useful, conservative prototype. It does not implement a general-purpose PDF editor or universal PDF-preservation guarantee. A whole-engine replacement is not justified by this review.

The strongest implementation is immutable originals → local transform → independent reader → atomic final result → read-only preview/save → remove → undo. Web and Apple have actual historical execution evidence. Android has partial native source and unexecuted native tests, and is currently disabled by an incomplete storage-capability bridge. The important unresolved native runtime observations are intermittent XCTest animation-idle waits, the iPhone visible-software-keyboard gap, and lack of physical-device evidence. They must not be described as PDF corruption or confirmed production deadlock.

Statuses mean: **IMPLEMENTED** = an active code path exists within its stated limits; **PARTIAL** = useful implementation with material scope/verification gaps; **PLANNED** = no executable implementation in the reviewed path; **BROKEN-SUSPECT** = a specific incompatible path or plausible failure is identified, with reproduction limits stated; **UNKNOWN** = the review cannot establish support. Historical passing evidence is stated separately from status.

## Prioritized findings

### PDF-01 — Decoded-image budget is not enforced at the browser JPEG decode boundary

**Priority P1. Status BROKEN-SUSPECT for the advertised workload bound; no crash/exploit reproduced. Disposition REFACTOR.**

Shared preflight reads a PDF image dictionary’s Width/Height and checks their product (`packages/web-pdf/src/engine.ts:18–20`). The browser recompressor then calls `createImageBitmap` and constructs an OffscreenCanvas using the decoded bitmap’s dimensions without first validating the JPEG’s own dimensions or comparing them with the PDF dictionary (`engine.ts:26–29`). The browser codec ignores its width/height arguments. Therefore the local JPEG decoder/allocation boundary has no application-level guarantee of the stated 12-million-pixel limit when encoded image dimensions disagree with the PDF dictionary. PDF.js inspection/maxImageSize is not a substitute for a guard on this separate decode call.

Apple checks JPEG metadata, exactly matches actual dimensions and only then creates the image (`AtepdfPDFEngine.swift:192–214`). Android checks decoded bounds before allocation (`AtepdfPdfEngine.kt:101–115`). The missing web check is a real source difference; actual browser allocation/rejection behavior for a hostile mismatch remains untested.

**Smallest complete correction after unfreeze:** validate encoded JPEG dimensions before bitmap creation, reject unsupported/mismatched dimensions and verify the returned dimensions before canvas allocation; retain cleanup. Add matching and mismatched JPEG fixtures, including a small declared dictionary paired with an over-budget encoded image, and assert refusal before codec allocation with no result commit. Do not infer that this alone makes whole-document parsing memory-bounded.

### PDF-02 — “Validated” means a limited semantic check, not complete page preservation

**Priority P1 before broad fidelity claims. Status PARTIAL. Disposition REFACTOR.**

`PageInfo` carries only width, height, rotation and text (`packages/web-pdf/src/types.ts:2`). The controller accepts equal dimensions/rotation and text after removing all whitespace and lowercasing (`job-controller.ts:11,85–95`). Two image-only pages with identical dimensions are indistinguishable to that comparison. Missing/reordered imagery, altered glyph positions, crop origins, font substitution, colors or equal-text pages can pass it. OCR checks that every recognized word appears somewhere in the extracted page string, not that its count, reading order or position is correct.

This does **not** establish that the current writer corrupts those PDFs. It establishes that the runtime validator cannot detect those classes of corruption. Apple’s 96-pixel inspection raster establishes renderability, not visual equivalence (`AtepdfPDFEngine.swift:90–95`). PDF.js’s operator list has an explicit regression showing it can omit oversized inline imagery without failing (`tests/regressions/content-admission.test.ts:27–37`); the separate admission guard correctly closes that particular case.

**Smallest complete correction after unfreeze:** first add a fixture oracle that checks all page boxes, raster anchors/page identity and text geometry across both independent readers. Keep compression’s allowed image-quality differences separate from merge/remove/OCR’s preservation requirements. Decide which inexpensive checks belong in runtime after the corpus shows their value. Preserve the existing semantic check and atomic commit barrier.

### PDF-03 — Retained output history eventually makes every new request invalid

**Priority P2. Status BROKEN-SUSPECT, deterministic source path; no execution during freeze. Disposition REFACTOR.**

`JobController.request()` serializes every stored original and output (`job-controller.ts:57`). The canonical request schema permits at most 100 files (`packages/contracts/schemas/planner-request.schema.json:27–75`). Every successful result remains in the store, including an output popped by Undo (`local-file-store.ts:25,28`). A job accepted with 100 stored artifacts can commit artifact101; the next request fails schema validation. For example, two originals plus99 outputs reach101 artifacts. `quick()` constructs the request before its own try block (`job-controller.ts:58–60`). Clear can recover, but discards the session and is not a good long-session policy.

**Smallest complete correction after unfreeze:** use a bounded actionable manifest containing selected originals/current focus and deliberately supported references, while retaining earlier result cards locally. Alternatively define an explicit bounded history policy with owner-approved retention semantics. Do not raise the schema limit indefinitely. Regression: more than100 successful small outputs, interleaved Undo, then a follow-up on the current result; original hashes and saved earlier output access must remain correct.

### PDF-04 — Removing the 20MB policy limit did not create bounded-memory large-document execution

**Priority P1 for large-file/device reliability; not an observed OOM. Status PARTIAL. Disposition REFACTOR.**

Files are fully read into ArrayBuffers (`job-controller.ts:43`), copied on get/prepare/commit (`local-file-store.ts:13–24`), parsed in full before drawing-content budgets apply (`engine.ts:8,22`), and multiple transform inputs are preflighted together (`engine.ts:31–34`). Browser workers receive structured-cloned input bytes (`client.ts:5–17`); native adds whole temporary-file and base64 codec transfers (`runtime.native.ts:26–36,47–54`). All originals/results remain in memory until Clear. The content decoder itself notes that an upstream compressed block may expand before its budget check (`content-admission.ts:3–5`).

There is no current 20MB PDF-byte admission gate in these paths. There **are** 20-original/session, 100-page/output, 15-OCR-page and pixel/content-workload limits. Those are distinct safety/scope controls, not SaaS upload limits. The large-byte fixture is genuine painted uncompressed RGB image data (`tests/helpers/large-pdf.ts:2–14`), not padding. Its successful history exceeding100MB is useful functional evidence, not a lower-memory physical-device ceiling or peak-memory benchmark.

**Smallest complete correction after unfreeze:** instrument peak memory and cancel responsiveness on representative physical devices, reduce avoidable copies, move the native writer off the UI JS execution path where feasible, and adopt a separate app-private file-backed session store only with an explicit cleanup/retention design. Use resource-aware admission based on actual device/workload rather than reinstating an arbitrary upload limit. No unlimited-size or hard allocation-safety claim is warranted now.

### PDF-05 — Android is unavailable through the current native runtime

**Priority P2, deferred platform; not an Apple/web blocker. Status BROKEN-SUSPECT integration. Disposition REFACTOR.**

The TypeScript native module contract requires `storageIsolated:boolean` (`apps/universal/modules/atepdf-pdf/index.ts:3–6`). Runtime’s `nativeEngineReady` requires it to equal true (`runtime.native.ts:15–18`). Android exports only readerAvailable and ocrAvailable (`AtepdfPdfModule.kt:15–18`), so storageIsolated is undefined and all local engine capabilities are disabled. Supplying true without implementing Android storage policy would be an unsafe shortcut. Android’s direct helper currently allows files/cache roots (`AtepdfPdfEngine.kt:169–188`), whereas Apple is narrowed to a dedicated work root.

**Smallest complete correction after unfreeze, only when Android resumes:** implement and test an Android-specific isolated-storage capability and dedicated roots, align cancellation bridge types, then run the native library and full application on API35+. OCR remains unavailable until separately implemented. The existing six instrumented tests have not been executed, per `docs/evidence/native/android-source-status.json`.

### PDF-06 — Cancellation prevents commit but does not guarantee prompt interruption of all local work

**Priority P2. Status PARTIAL. Disposition KEEP commit safety; REFACTOR latency with measurements.**

Web transform cancellation terminates a worker (`client.ts:5–17`). Native shared transforms run in JS and yield only at selected checkpoints (`runtime.native.ts:47–54`; `engine.ts:35–47,92`); CoreGraphics drawing is synchronous (`AtepdfPDFEngine.swift:262–287`). Apple tokens are created when work begins on a serial queue (`AtepdfPdfModule.swift:56–76`), so a previously queued call can begin after a cancel generation change. JS still checks the aborted signal and discards its result. The cancellation drain prevents an old asynchronous native cancel from striking the next job (`native-cancellation.ts:2–12`), and is covered by ordering tests.

The 120/240-second checks are not preemptive CPU/memory containment. Preview unmount deletes its returned image when it eventually arrives; it does not cancel synchronous native drawing (`Preview.native.tsx:65–74`). This can leave transient work after closing a preview without promoting an output.

**Minimum follow-up:** native queued-preview → cancel → new job ordering, cancel during real OCR, and measured cancel latency during a large parse/render. Keep “no cancelled candidate committed” separate from “work stopped immediately.” Existing late-cancel drain tests are valuable and should remain.

### PDF-07 — Difficult-PDF coverage is substantially narrower than the admission and preservation claims

**Priority P1 for broad beta compatibility; P2 within the documented narrow synthetic slice. Status PARTIAL/UNKNOWN by row below. Disposition KEEP current tests; REFACTOR corpus.**

No actual encrypted PDF fixture, real AcroForm/widget/link/annotation preservation fixture, complex multilingual font corpus, mixed-size merge corpus, or successful100-page shared-engine job was found in the reviewed tests. Rejecting fabricated empty feature dictionaries tests branch coverage, not realistic PDF compatibility. `tests/fixtures/expectations.json` explicitly describes its pack as small synthetic inputs and does not list the separately added image-heavy PDF. These gaps are not closed by a large count of UI, planner or billing tests.
